The Prestige Collection Flutter app implements a basic JWT-based authentication system with storage via SharedPreferences. While the core authentication flow is functional, there are several critical security gaps that require immediate attention, particularly around token refresh/expiration, credential handling, and secure storage mechanisms.

Detailed Findings

CRITICAL No Token Expiration or Refresh Mechanism
The application does not implement token refresh or expiration handling. Once a JWT expires on the backend, the stored token remains valid in the app until manually cleared or the user logs out.
Current Code (api_service.dart):
• Tokens are saved without storing expiration time
• No mechanism to refresh expired tokens
• No interceptor to detect 401/403 responses and trigger re-authentication
• Users may continue using the app with an invalid backend token
Recommendation: Implement a token refresh strategy:
  1. Store token expiration time alongside the token
  2. Add a refresh token mechanism (if backend supports it)
  3. Implement automatic token refresh before expiration
  4. Handle 401 responses by attempting token refresh or forcing re-login
CRITICAL Plaintext Token Storage in SharedPreferences
JWT tokens are stored unencrypted in SharedPreferences, which on Android is accessible to other apps through file permissions. An attacker with device access could retrieve the token and impersonate the user.
Affected Code (storage_service.dart, line 12):
await prefs.setString(_tokenKey, token);

Risk Assessment:
• SharedPreferences uses XML files stored in app data directory
• On Android, root apps or users with adb access can read these files
• On iOS, encryption is better but still accessible via physical device access
• JWT contains sensitive user claims (userId, email)
Recommendation: Use secure storage:
  • Android: Use EncryptedSharedPreferences (androidx.security:security-crypto)
  • iOS: Use Keychain via flutter_secure_storage package
  • Cross-platform: Implement flutter_secure_storage package
Add to pubspec.yaml:
flutter_secure_storage: ^9.0.0
HIGH No SSL/TLS Certificate Pinning
The HTTP client does not implement certificate pinning, making it vulnerable to man-in-the-middle (MITM) attacks on networks with compromised or malicious proxies.
Current Implementation (api_service.dart):
final httpClient = _getHttpClient();

The basic http.Client() provides no certificate validation customization.
A MITM attacker could intercept login requests and steal credentials or tokens.
Recommendation: Implement certificate pinning:
  • Add http_certificate_pinning package: http_certificate_pinning: ^2.0.0
  • Pin your backend's SSL certificate or public key
  • Implement a custom HttpClient with pinning validation
  • Test on both iOS and Android devices
HIGH No Timeout for Token Validation
While individual API calls have 30-second timeouts, the token itself is never validated for integrity or age before use, and there is no mechanism to handle token corruption or expiration.
Problem: An expired, revoked, or corrupted token will be sent to the backend on every request until the user manually logs out. The app doesn't proactively check token validity.
Recommendation: Add token validation on app startup:
  1. Validate JWT signature using the public key from backend
  2. Check token expiration time before making requests
  3. Implement SplashScreen validation: call a /api/auth/validate endpoint
  4. Force re-login if token is invalid or expired
HIGH Password Sent Over Network Without HTTPS Verification
Login requests send plaintext passwords to the backend. Without mandatory HTTPS and certificate pinning, these credentials are vulnerable to interception.
Affected Code (api_service.dart, lines 75-78):
body: json.encode({
'email': email,
'password': password,
})

While the API_BASE_URL is configurable, there's no enforcement that it uses HTTPS or validation of the certificate.
Recommendation:
  • Enforce HTTPS-only API URLs (validate in ApiConfig.baseUrl)
  • Implement certificate pinning (see HIGH finding above)
  • Document that the app only works with HTTPS endpoints in production
  • Add build-time validation: log warning if API_BASE_URL is http:// in production builds
MEDIUM Credential Logging in Debug Output
The error handler uses debugPrint() to log detailed API responses, which could expose sensitive error messages or incomplete data that hints at system internals.
Affected Code (api_service.dart, lines 42, 57, 99):
debugPrint('API Error (${response.statusCode}): ${response.body}');
debugPrint('Login error: ${e.toString()}');

While debugPrint() is disabled in release builds, the practice of logging full error bodies could expose information during development or in crash logs.
Recommendation:
  • Never log full response bodies; log only status codes and high-level error types
  • Sanitize error messages before displaying to users (already done correctly)
  • Implement structured logging with appropriate log levels
  • Use a crash reporting service (Sentry, Crashlytics) with PII filtering
LOW No CSRF Protection Consideration
The app does not implement CSRF tokens or validate CSRF headers. While Flutter apps are less vulnerable to CSRF than web apps (no cookies are auto-sent), the backend should still implement CSRF protection.
Impact: If the user is also logged into the backend via a web session, a malicious website could potentially perform actions on the user's behalf.
Recommendation:
  • Ensure backend implements CSRF protection for its web clients
  • For Flutter, verify that the backend does not rely on cookies for auth (JWT is correct)
  • No action required in Flutter app unless backend returns CSRF tokens
INFO Opportunity: Implement Request Signing
The API currently relies solely on JWT bearer tokens for authentication. Adding request signature validation would provide defense-in-depth.
Optional Enhancement:
Request signing (HMAC-SHA256) ensures request integrity and can prevent certain attack vectors. This is typically used for high-security APIs.
Recommendation:
  • Document the current JWT-only approach as sufficient for e-commerce use case
  • If financial transactions are added, consider implementing request signing
  • Coordinate with backend team on signing algorithm

The authentication implementation has several critical and high-priority security vulnerabilities that require immediate attention. The primary concerns involve insecure token storage, lack of HTTPS enforcement, and unvalidated error messages that may expose sensitive information.

🔒Security Findings

CRITICAL JWT Token Stored in SharedPreferences (Plaintext)
The JWT access token is stored unencrypted in SharedPreferences, which provides only minimal protection on mobile devices. SharedPreferences uses a plain XML file on Android and a property list on iOS—both readable to other apps or via device backups.
// storage_service.dart, lines 10-13 static Future<void> saveToken(String token) async { final prefs = await SharedPreferences.getInstance(); await prefs.setString(_tokenKey, token); }
Use platform-specific secure storage: Keychain on iOS and Keystore on Android via the flutter_secure_storage package. This stores credentials encrypted and isolated from other app data.
HIGH Lack of HTTPS Enforcement & Certificate Pinning
The default API base URL defaults to http://127.0.0.1:3000, and the application does not enforce HTTPS in production. There is no certificate pinning implemented, making the application vulnerable to man-in-the-middle (MITM) attacks, particularly on untrusted networks.
// api_config.dart, line 8 defaultValue: 'http://127.0.0.1:3000',
Add environment-based configuration to enforce HTTPS in production. Implement certificate pinning using the http_certificate_pinning or dio package with pinning support. Validate that production deployments use HTTPS exclusively.
HIGH Missing JWT Token Validation & Expiration Checking
The application retrieves and uses tokens without validating their signature, checking expiration, or verifying claims. An expired or tampered token would still be transmitted to the server, relying entirely on server-side validation.
// api_service.dart, lines 50-55 if (includeAuth) { final token = await StorageService.getToken(); if (token != null) { headers['Authorization'] = 'Bearer $token'; } }
Implement JWT validation on the client side using the jwt_decoder package. Check token expiration before making requests and refresh tokens automatically when expired. Parse and validate the JWT structure before transmission.
HIGH Missing Token Refresh Mechanism & Long-Lived Token Vulnerability
The system stores only an accessToken without a refresh token. If tokens have extended expiration (e.g., 7 days as suggested by JWT_EXPIRES_IN=7d), a stolen token could be valid for an extended period. No mechanism exists to invalidate tokens server-side.
// auth_response_model.dart, line 4 final String accessToken;
Implement the OAuth2 refresh token pattern. Store both short-lived access tokens (15-60 minutes) and longer-lived refresh tokens securely. Implement automatic token refresh before expiration. Add server-side token blacklisting for logout functionality.
MEDIUM Verbose Error Messages Exposing Sensitive Information
The application returns full error messages and URL information in exceptions, which may expose backend structure or internal details to users or logs.
// api_service.dart, line 199 throw Exception('${_handleError(response)} (URL: $loginUrl)');
Implement user-friendly error messages separate from technical details. Log full error information server-side only. Return generic messages to clients like "Authentication failed. Please try again." Avoid exposing API URLs or backend structure in error responses.
MEDIUM Missing Request Timeout on Most Endpoints
Most HTTP requests lack timeout configuration, except for the initial URL resolution in initializeBaseUrl() (line 23). Long-hanging requests can exhaust resources and enable denial-of-service scenarios.
// api_service.dart, line 179 final response = await http.post( Uri.parse(loginUrl), headers: await _getHeaders(includeAuth: false), body: json.encode({...}), ); // No timeout specified
Add consistent timeout configuration to all HTTP requests. Use a centralized timeout setting (e.g., 30 seconds for most requests, 60 seconds for file uploads). Implement exponential backoff for retries.
LOW No CSRF Token Handling for State-Changing Operations
While CSRF is less relevant for mobile apps due to their sandboxed nature, the absence of CSRF token handling is noted for completeness. All state-changing operations (POST, PATCH, DELETE) rely solely on bearer token authentication.
For web deployments, implement CSRF token handling. Ensure backend implements proper SameSite cookie policies and CORS restrictions. This is low priority for mobile but important if the Flutter app shares authentication with web clients.
LOW Minimal Client-Side Input Validation Before API Calls
The API service accepts parameters without validation. For example, login() doesn't validate email format, and cart operations don't validate quantity ranges before transmission.
// api_service.dart, lines 175-186 static Future<AuthResponseModel> login(String email, String password) async { // No email format validation // No password length validation final response = await http.post(...); }
Add lightweight client-side validation using packages like validators or form_validation. Validate email format, password strength, and quantity bounds before API transmission. This improves UX and reduces unnecessary server load.

📦Token Storage & Transmission Security

Storage Location Analysis

Android: SharedPreferences stores data in /data/data/<package>/shared_prefs/ as plaintext XML. Readable by the same app, device owner with access, or apps with READ_EXTERNAL_STORAGE permission.

iOS: SharedPreferences (NSUserDefaults) stores data in ~/Library/Preferences/<bundle-id>.plist with no encryption by default. Protected by iOS app sandbox but not by additional cryptographic layers.

Transmission Analysis

Protocol: Bearer token transmission is RFC 6750 compliant, properly formatted in the Authorization header.

Vulnerability: Without HTTPS enforcement, the bearer token is transmitted in plaintext over the network, vulnerable to:

  • Network sniffing on unencrypted connections
  • Man-in-the-middle (MITM) attacks
  • Interception on public/untrusted WiFi networks
